## Overview

Parkomat.Agent is a **Windows-only .NET 10 / C#** agent that runs on a PC at a parking
site. It reads a PLC over **Modbus-TCP** and relays the site's state to the cloud
(**HiveMQ**) over **MQTT**, through a local **Mosquitto** bridge.

End-to-end data flow:

```
PLC → (Modbus-TCP) → Agent Service → (MQTT localhost:1883) → Mosquitto → (bridge/TLS) → HiveMQ → server
```

## Solution layout

`Parkomat.Agent.slnx` contains three projects under `src/`:

| Project | TFM | Responsibility |
|---|---|---|
| **Parkomat.Agent.Core** | `net10.0` | Shared config + protocol. Referenced by both other projects. `AgentPaths`, `ConfigStore`, `SiteConfig`, `SiteState`, `ModeTranslator`, `Messages`. |
| **Parkomat.Agent.Service** | `net10.0` | The Windows Service — the background heart. `Worker.cs` loop; `PlcReader` (NModbus), `OperationDetector`, `MqttPublisher` (MQTTnet), `BridgeConfigWriter`. |
| **Parkomat.Agent.Tray** | `net10.0-windows` | WinForms tray app for managing the service. `TrayContext`, `ServiceManager`, `SettingsForm`, `RegistersForm`. |

## Build / run / publish

Run from the `Parkomat.Agent/` directory:

```sh
# Build the whole solution
dotnet build Parkomat.Agent.slnx

# Run the Service locally as a console app (dev; DOTNET_ENVIRONMENT=Development via launchSettings)
dotnet run --project src/Parkomat.Agent.Service

# Run the Tray app
dotnet run --project src/Parkomat.Agent.Tray

# Run tests
dotnet test Parkomat.Agent.slnx

# Publish for deployment — output paths MUST match what installer.iss expects
# (publish/service, publish/tray).
#
# SelfContained + RuntimeIdentifier now live in BOTH .csproj files, so a plain
# `dotnet publish` is already correct and the flags cannot be forgotten. That
# move was not tidying: the flags used to exist only on the command line, one
# publish went out without them, and the result was a build that demanded
# ".NET 10 must be installed" on every site PC.
#
# ⚠️ ALWAYS wipe the output directory first. `dotnet publish` overwrites files;
# it does NOT remove ones it no longer produces. Publishing framework-dependent
# over a previous self-contained folder leaves the old runtime DLLs sitting
# next to an app that now asks for the runtime from outside.
rm -rf publish/service publish/tray
dotnet publish src/Parkomat.Agent.Service -c Release -o publish/service
dotnet publish src/Parkomat.Agent.Tray    -c Release -o publish/tray
```

### Verifying the build is self-contained — check the file, not the size

The installer's **size does not prove it**, and that guess is what let the bad build ship. The
stale runtime DLLs left behind by the previous publish were packaged too, so the framework-
dependent installer still weighed ~64MB — exactly the size a correct one weighs. It looked
right and would not start.

The single authoritative check is one word in `publish/service/*.runtimeconfig.json`:

| | |
|---|---|
| `"includedFrameworks"` | ✅ the runtime is inside — runs anywhere |
| `"framework"` / `"frameworks"` | ❌ demands .NET 10 be installed on the site PC |

Stronger still, and it takes one line — hide .NET from the process and see it start anyway:

```sh
DOTNET_ROOT=/nonexistent ./publish/service/Parkomat.Agent.Service.exe
# expect: "Application started."   (self-contained ignores DOTNET_ROOT)
```

Installer: **Inno Setup** compiles `installer.iss` → `installer-output/ParkomatAgentSetup.exe`.

Tests live in `tests/Parkomat.Agent.Service.Tests` (xUnit). Current coverage is the
`OperationDetector` state/operation logic. For behavior with no unit coverage (PLC I/O, MQTT),
verify by running the Service/Tray directly.

## Runtime data locations

All paths come from `AgentPaths` (`src/Parkomat.Agent.Core/Configuration/AgentPaths.cs`).
Base folder is `C:\ProgramData\Parkomat\Agent\` — shared so both the Service (runs as SYSTEM)
and the Tray (runs as the user) can read/write it:

- `config.json` — site + PLC + MQTT settings (`ConfigStore` / `SiteConfig`)
- `heartbeat` — unix seconds, written after each **successful PLC read**. Drives the tray
  icon: a site whose PLC is dead must look grey.
- `alive` — unix seconds, written **every loop iteration** regardless of PLC outcome (and
  inside the pending-operations drain). Drives the watchdog's wedged decision only.
- `detector-state` — `<unix> <mode> <card>`. Lets a restart resume instead of opening a
  phantom operation. Rejected if older than `DetectorState.MaxAge` (10 min).
- `bridge.conf` — Mosquitto bridge config, generated by `BridgeConfigWriter`
- `queue/` — one file per operation not yet published. **Survives a power cut.**
  See *The queue survives a power cut* below.
- `agent.db` — reserved (declared path; not yet used)

> ⚠️ **`heartbeat` and `alive` answer different questions — never merge them.** They were the
> same file once, and it cost sites their fault reporting. See "Watchdog" below.

## Architecture & control flow

`Worker.cs` (`ExecuteAsync`) runs the main loop: **read PLC → feed the brain → publish**.

- **`OperationDetector`** is the pure "brain": it *decides* what to publish and never sends
  anything itself. It remembers the previous MODE in `_previousMode` and emits a `state`
  message when the translated state changes, plus `operation` start/end messages on
  entry/exit transitions.
- **PLC failure handling:** 10 consecutive failed reads → publish `state: error` **once**
  (guarded by `plcErrorReported`), reset when the PLC recovers.
- **Heartbeat:** written on every successful read. The Tray (`ServiceManager`) reads it back
  to distinguish "really working" (heartbeat fresh ≤ 10s → colored icon) from merely
  "process alive" (service running but no fresh heartbeat).

## Watchdog — liveness is not the same as a healthy PLC

The Tray restarts the agent when it looks stuck. **The stuck decision reads `alive`, never
`heartbeat`**, and the difference is not cosmetic:

`heartbeat` is only written after a *successful* PLC read, so a dead PLC looked exactly like
a wedged process. Measured: a failed read costs ~3.2s (TCP connect timeout), so the 10
consecutive failures needed to publish `state: error` take ~42s — against a 30s wedged
threshold. **The agent was killed 12s before it could report**, and the kill reset the failure
counter, so `error` was never published at all. Sites flapped between `no_comm` and restart,
and nobody could tell "PLC dead" from "PC off".

- The decision itself lives in **`WatchdogPolicy.Decide`** — a pure function, same pattern as
  `RestartPolicy` and `ResyncPolicy`. `ServiceManager` only gathers file ages and executes.
  It was untestable before, which is precisely why the bug survived 127 passing tests: every
  policy was correct alone, and nothing tested the interaction.
- **Missing `alive` → never wedged.** Covers both a fresh install that has not completed an
  iteration and an older agent that does not write the file. Failing safe beats a kill loop.
- `WatchdogVsPlcErrorTests` pins the timing relationship so the thresholds cannot drift back
  into overlapping.

## A restart must not invent an operation

`OperationDetector` is edge-triggered, so with no previous MODE a first reading inside MODE
2/3 opens an operation stamped *now*. Correct on a fresh install; wrong after a restart,
where the operation was already open. The server's dedup key is the reported timestamp, so
**every restart produced another operation row** — and since the failure-rate denominator is
the operation count, a site that restart-looped scored *healthier* the more broken it was.

`Worker` now loads `DetectorState` at startup and calls `detector.Restore(...)`, so an
unchanged MODE produces nothing and a changed one produces a real end/start pair.

- **The age bound is load-bearing.** Stale state would emit an `end` stamped *now* for an
  operation that finished long ago — a several-minute "entry". 10 minutes covers the longest
  restart backoff (`RestartPolicy.MaxDelaySeconds` = 300) and stops well short of that.
  `DetectorRestoreTests` pins that relationship.
- `Restore` throws if called after processing has begun — mid-run it would overwrite live
  state and synthesise a transition.
- State is written only when MODE or the card changes, not every poll.

## Known limit: the cycle counter is 16 bits

`CycleRegister` is a single Modbus register, so the counter caps at 65,535 and wraps. The
server reads a decrease as a controller reset and drops the delta (`applyCycleCounter`), so
each wrap silently loses up to 65,535 cycles.

**This is deliberately not "fixed" in the agent.** A wrap (65,530 → 5) and a genuine reset
(65,530 → 0) are indistinguishable from the value alone; auto-adding 65,536 on every decrease
would inflate the counter on every real reset. Instead `Worker` logs a warning on any drop.
If drops cluster near 65,535 the counter is wider than one register and should be read as
32 bits across two; if they come from arbitrary values, they are real resets.

## MQTT / server contract (non-obvious — easy to break)

These are enforced by the server; changing them silently breaks ingestion:

- **Topics:** `sites/{siteId}/state`, `sites/{siteId}/operation`, and `sites/{siteId}/bridge`
  (the last one is published by **Mosquitto**, not by us — see "Disconnect detection" below).
- **Timestamps are unix _seconds_, not milliseconds.** The server floors its own timestamps to
  whole seconds to match; a mismatch here strands sites in `no_comm` permanently.
- **`SiteState` JSON strings are exact and server-enforced:** `ready`, `operating`, `error`,
  `maintenance`, `no_comm` (see `SiteState.cs` `[JsonStringEnumMemberName]`). Do not rename.
- **Operation messages must include a valid `state`** or the server rejects them.
- **`user` (card number) must be `""`, never `null`** — it is part of the server's dedup key.
- **The Service always connects to local Mosquitto (`localhost:1883`), never directly to
  HiveMQ.** The `MqttConfig` host/port/username/password feed the generated `bridge.conf`
  (`BridgeConfigWriter`) — they are *not* the client connection settings.

## Disconnect detection — two LWT layers (do not collapse them)

⚠️ **This is about the MQTT path, and stays true of it.** The *direct* path does have a
heartbeat (see *The heartbeat* below) — it exists precisely because switching HiveMQ off also
removes the will.

There is no heartbeat and no server-side watchdog. "90 seconds" is **1.5 × the 60s keepalive**,
enforced by the brokers. Two layers, because one is not enough:

1. **Agent → local Mosquitto.** Our LWT: JSON `{"timestamp":0,"state":"no_comm"}` on the state
   topic. Covers: *the agent process crashed while the PC kept running.*
2. **Mosquitto bridge → HiveMQ.** Mosquitto's own bridge notification, payload `"1"`/`"0"` on
   `sites/{siteId}/bridge`. Covers: **the PC lost power.** In that case Mosquitto dies together
   with the agent, so *nobody local is left to publish layer 1* — only HiveMQ, which holds the
   bridge's will, can report it.

Layer 2 is the failure that actually matters at a car park, and it was silently broken:
`bridge.conf` had `notifications_local_only true`, so the notice stayed on a **powered-off PC**
and the server showed the site as healthy indefinitely. `BridgeConfigWriter` now sets
`notifications_local_only false` and an explicit `keepalive_interval 60`. Do not "tidy" these away.

The payload is `"1"`/`"0"`, **not JSON** — which is exactly why it needs its own topic and cannot
share `sites/{siteId}/state`, where the server contract demands JSON.

On bridge reconnect the agent **republishes its current state with a fresh timestamp**
(`Worker.cs`). Without that resync, messages queued during the outage carry old timestamps, the
server's backfill guard rejects them, and the site stays `no_comm` after it has already recovered.

## TLS is mandatory and cannot be switched off

`MqttConfig` has **no `UseTls` field**, and the settings form has no checkbox — both were
removed on purpose. The bridge carries the site's username and password to HiveMQ across the open
internet; without TLS they travel in clear text. A checkbox there was not flexibility but a trap:
one click by a technician in the field silently downgraded the whole site, and nothing failed
loudly. `BridgeConfigWriter` always emits `bridge_tls_version tlsv1.2` + `bridge_cafile`.

The CA certificate lives under `ProgramData` (no spaces in the path), not `Program Files`.
- **MODE → state mapping lives only in `ModeTranslator`:** `0`=maintenance, `1`=ready,
  `2`/`3`=operating, `4`=init (ignored, no state), `5`=error. For operations, `2`=entry,
  `3`=exit.

## Conventions

- Source comments are in **Hebrew** — match that when editing existing files.
- `Nullable` and `ImplicitUsings` are enabled across projects.
- **Atomic file writes** (write to `.tmp`, then `File.Move(..., overwrite: true)`) in

## Deployment notes

`installer.iss` is a **per-user, no-admin** install (`PrivilegesRequired=lowest`, no UAC
prompt). It does **not** register any Windows service and does **not** use `nssm`. Everything
runs in the user's session:

- The install goes to `{localappdata}\Parkomat\Agent` (service + tray + bundled Mosquitto).
- The **Tray** auto-starts per-user via an **`HKCU\...\Run`** registry value (not `HKLM`).
- The Tray is the supervisor: it launches and watchdogs **both** the Agent process and
  **Mosquitto** as ordinary child processes (no services). Runtime data still lives under
  the shared `C:\ProgramData\Parkomat\Agent` path (a standard user may create/own it).

> Nothing in install or runtime requires administrator rights. `PrepareToInstall` does make
> best-effort `sc.exe stop/delete` calls to clean up an **older admin-era** install; without
> admin those simply fail silently (no UAC, no error) and the install proceeds. Do not
> reintroduce a service-based (`nssm` / `sc create`) install — it would bring back the admin
> requirement this design deliberately removed.

## The queue survives a power cut — and `cleansession` was a measured lie

Written in English like the rest of this file.

Two halves of one failure, both closed on 01/09/2026.

**Half one: `cleansession true` in the bridge block.** It was the only line in
`BridgeConfigWriter` without a rationale, and it silently meant that **every message
produced during an internet outage was lost forever** — not delayed, lost. Measured in a
controlled experiment (`tools/cleansession-test.sh`: two local brokers, identical config,
deliberate disconnect, five QoS-1 messages):

```
cleansession true   ->  0 of 5 arrived
cleansession false  ->  5 of 5 arrived
```

⚠️ **And the comment in `Worker.cs` asserted the opposite** — *"Mosquitto accumulates the
messages and streams them when the bridge returns"*. It described an intent that never
happened. Both were corrected together.

⚠️ **The first measurement was wrong and looked like a result.** It reported 0/5 for *both*
variants, because the subscriber came up *after* the bridge had already delivered. Only
reading the broker's own log gave the real answer. `BridgeQueueingTests` pins the value; the
mutation back to `true` fails it.

**What it recovers, precisely:** queued messages carry their **original** timestamps, so
**operations** are ingested (the server dedups on `occurred_at`, and this is genuine
backfill — it is the business data). **Late `state` messages are still rejected** by the
backfill guard, and that is correct: the resync on reconnect already delivered the current
state with a fresh stamp.

**Half two: the queue lived in memory.** `Worker.cs` documented the gap itself — *"the queue
lives in memory only, so every operation it exists to save would be lost right here"* — and
the line beneath it was a `List`. `PendingQueue` (`Core/Queue/PendingQueue.cs`) writes one
file per pending operation under `AgentPaths.QueueFolder`.

- **One file per message, not one file with an index.** A central index must be rewritten on
  every removal, and a write interrupted mid-way leaves it corrupt — *a structure meant to
  prevent loss becomes a source of loss*. A separate file is written atomically (`.tmp` then
  `Move`) and deleted atomically; there is no in-between state. Same pattern `ConfigStore`
  and `BridgeConfigWriter` already follow.
- **Operations only, deliberately.** An operation is a one-shot event — the detector is
  edge-triggered and advances immediately, so a missed transition cannot be re-detected. A
  *state* repairs itself: on start-up the agent resyncs with a **fresh** stamp. Queuing state
  would be work whose outcome is rejection.
- **The filename is `{millis:D13}-{seq:D4}`.** Two fields, because one MODE change produces
  two operations in the same millisecond and without the counter the second overwrites the
  first. The 13-digit padding is what makes a *lexical* sort chronological.
- A corrupt file is skipped, not fatal — one truncated file would otherwise block the whole
  queue behind it forever, the exact opposite of the point.

⚠️ **What is still not covered:** the queue only protects what the agent has *produced*. A
PLC reading never taken is not recoverable by anything.

## Direct write to Supabase — built, tested, and **off**

The agent can write straight to Postgres through PostgREST, bypassing MQTT entirely. It
ships **disabled** and stays that way until **one field** — the site password — is filled in.

```
PLC -> Agent --+-> (MQTT) -> Mosquitto -> HiveMQ -> server -> Supabase
               +-> (HTTPS) --------------------------------> Supabase   <- only when configured
```

- **`SupabaseConfig.Enabled` is *derived*, never stored.** A separate boolean would allow
  "on but incomplete" — an agent that tries every cycle, fails every cycle, and fills the
  log. That state cannot be expressed here.
- ⚠️ **One field, not four — and the other three were removed, not hidden.** The project URL
  and publishable key are the same at every site (`SupabaseDefaults`), and the user name is
  derived: `site-{SiteId}@parkomat.co.il`, which must stay byte-identical to `emailFor` in
  `tools/provision-agent-user.js` or the agent signs in as a user that was never created.
  `ConfigStore.Load` stamps `SiteId` onto the Supabase settings — without it the derivation
  runs on an empty string, `Enabled` stays false forever, and **nothing is logged**: the
  direct write simply never happens and it looks exactly like "this site was not switched on".
- **The overrides (`Url`, `AnonKey`, `Email`) stay in `config.json` but not in the form.**
  They are the exit door — repointing to another Postgres without touching 16 installers. The
  form carries them through `OnSave` in `_sbOverrides` because it rebuilds `SiteConfig` from
  scratch, and without that every "Save" would silently reset a repointed site.
- **Dual write, MQTT authoritative.** The direct path is best-effort: a failed batch is
  logged and *not* retried, because the message already went out over MQTT. Same staging
  pattern as `VITE_SUPABASE_DIRECT` in the dashboard and the dormant auth provider.
- **One seam, not six call sites.** `Worker` publishes from six places, several building the
  message inline. Mirroring at each would be a matter of memory — *a seventh site added
  tomorrow would reach nobody*, with no error and no sign, and it would surface only on the
  day MQTT is switched off. So the observer (`MqttPublisher.OnPublished`) sits in
  `PublishAsync`, which every publish already funnels through, right beside `SentAuditLog`.
  It fires **only after a successful publish**, and is wrapped in `try/catch` — an exception
  from the secondary path that kills an MQTT publish turns *a new route failing* into
  *breaking the old route that works*.
- ⚠️ **The batch is cleared at the *start* of each cycle**, not only after a successful send.
  A cycle that throws before the send skips the trailing clear, and the batch would grow
  every cycle until it exceeds the server's 200-message cap — after which **every** send is
  rejected, forever, because of one cycle that failed an hour ago.
- **The server derives the site from the identity, never from the payload.**
  `public.ingest_batch` takes no site id; `app.agent_site_id()` supplies it. An agent that
  received the site as a parameter could write to any other site by changing one number.

### The heartbeat — `BeatAsync`, every 60 seconds

The agent sends an **empty batch** when it has nothing to say. That is the whole signal: *the
agent is alive and the network works.* `app.mark_silent_agents` in Postgres marks any site
whose last beat is older than 3 minutes as `no_comm` — the replacement for MQTT's will once
HiveMQ is switched off.

- **60 seconds is not a new cadence.** `bridge.conf` already sets `keepalive_interval 60`, so
  every site already emits a PINGREQ per minute; the server's "90 second rule" is 1.5 × it.
  The move to HTTPS changes the *carrier*, not the rate.
- ⚠️ **`BeatAsync`, never `SendAsync([])` — and this was a real, shipped bug.** `SendAsync`
  short-circuits an empty list with `Success(0)` **before** it touches the network. The first
  heartbeat called it, so every beat reported success, `lastBeat` advanced, and **not one
  request was ever sent**. Three tests passed on it, because all three matched patterns in
  `Worker.cs` instead of counting requests. `SupabaseWriterTests` now asserts the request
  actually appears in the fake handler's list — a structural test could not have caught this
  and did not.
- **The stamp advances only on success.** A beat that failed on the network is not a sign of
  life that arrived, and recording it would delay the next attempt by a full minute — exactly
  when the link is shaky.
- **`lastBeat` starts at `MinValue`**, so the first beat goes out immediately at start-up. An
  agent that just came back from a power cut must look alive at once, not in a minute.
- **`LogDebug`, not `LogInformation`** — 1,440 lines a day would bury everything that matters.
- **The version rides along** (`AssemblyInformationalVersion`, trimmed at `+` to drop the
  commit sha). It answers *"which agent is at which site"*, which nothing else does; the
  server keeps the previous value when a beat omits it.

### The contract is one file, pinned from both sides

`shared/contracts/ingest-batch.sample.json` is the source of truth for the request body.
`IngestContractTests` asserts the C# produces exactly it; `check-agent-write` (server) sends
it verbatim to PostgREST. **Neither side can move alone.**

⚠️ It earned its place on the first run: `System.Text.Json` escapes every non-ASCII
character, so a Hebrew fault text went out as `מיט…`. Valid JSON, decoded
correctly — but six times larger, and stored that way in `ingest_drops.payload`, so whoever
investigates a dropped message in six months reads gibberish instead of the line they came
for. Fixed with `UnicodeRanges.All` (not `UnsafeRelaxed` — `<`, `>`, `&` stay escaped).

### `check-agent-live` — the only test that crosses both languages *and* the network

`SupabaseWriterTests` uses a fake handler; `IngestContractTests` compares strings;
`check-agent-write` sends from Node. None of them proves the code that will run at a site
sends one valid byte. The gate provisions a synthetic site and agent, runs `dotnet test` on
the live test with environment variables, **and then asks the database whether the rows
landed**.

⚠️ **The gate — not `dotnet test` — is the authority on whether the test ran.** An xUnit test
that skips silently looks exactly as green as one that passed, and this project has been
burned by that before (three gates reported "did not run" for months). Verified by mutation:
with the test skipping unconditionally, `dotnet test` reports **Passed!** and the gate fails
on *"zero operations: the test finished green without sending anything"*.

## The version lives in one place

`Directory.Build.props` holds `<Version>`; neither `.csproj` declares its own (one that does
**silently overrides** the shared value — that is exactly how the drift started).
`installer.iss` is Inno Setup, not MSBuild, and cannot be wired to it, so `AgentVersionTests`
locks the equality instead — including against the **compiled assembly**, so a props file that
failed to load cannot pass unnoticed.

⚠️ The drift was real: both `.csproj` said `1.0.20` while `installer.iss` said `1.0.21` — the
installer announced a version its own binaries did not carry. And `installer.iss` documents
why that matters: the version number is the **only** way to know which agent is installed at
which site. The agent publishes its version on no topic, and Windows' program list is the only
place it appears.

`VersionInfoVersion` also stamps the setup **file itself**, which answers a question asked
earlier: a technician with three `ParkomatAgentSetup.exe` in Downloads — which one is newest?
Without it the file properties are blank and the only answer is the modified date, which
changes on every copy.
